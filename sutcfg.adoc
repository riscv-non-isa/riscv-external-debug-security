[[sutcfg]]
== Sutcfg (ISA Extension)

This chapter specifies the Sutcfg ISA extension, which provides U-mode and VU-mode access to Sdtrig cite:[dbgspec] triggers using the user-level indirect CSR interface defined by <<sucsrind, Sucsrind>>. Sutcfg is not a member of the Secure Debug or Secure Trace families.

When S-mode is implemented, U-mode access requires `mstateen0`.TR=1 and `sstateen0`.TR=1. When V=1, VU-mode access additionally requires `hstateen0`.TR=1 and virtual `sstateen0`.TR=1. When S-mode is not implemented, `mstateen0`.TR directly controls U-mode access.

Sutcfg enables:

* U-mode and VU-mode self-hosted debuggers to access triggers using `uiselect` and `uireg*`.
* An external debugger to access triggers through `uiselect` and `uireg*` when a Secure Debug extension is implemented and Debug Mode has less than M-mode privilege.

Sutcfg is a distinct extension. Its implementation requires Sucsrind. When S-mode is implemented, Sutcfg also requires <<smtdeleg, Smtdeleg and Sstcfg>>.

[[utrig-access]]
=== User Trigger Access

[NOTE]
The `uiselect` value for trigger access is to be allocated from the Sucsrind select address space. When <<smtdeleg, Smtdeleg and Sstcfg>> are implemented, the same value is used for `siselect` trigger access. Throughout this document, this value is referred to as the _trigger access value_. See <<trig-access-value>>.

While `uiselect` holds the trigger access value, `uireg5` provides user-mode read/write access to the trigger selection index, and `uireg` through `uireg4` provide user-mode read/write access to register state associated with the trigger selected by that index, the same state accessed by M-mode CSRs `tdata*` and `tinfo`. The register mapping is shown below.

.Indirect Trigger Register Mappings When `uiselect` Holds the Trigger Access Value
[cols="30%,70%", options="header"]
|===
| Indirect CSR | State Accessed
| `uireg`  | Same as `tdata1`
| `uireg2` | Same as `tdata2`
| `uireg3` | Same as `tdata3`
| `uireg4` | Same as `tinfo` (read-only; writes ignored), with type bits restricted as specified in <<utrig-type-constraints>>
| `uireg5` | Same as `tselect` (trigger selection index), as specified in <<utrig-select>>
|===

[NOTE]
Placing the selection index in `uireg5`, an alias otherwise unused by the trigger mapping, avoids consuming a user-level direct CSR address. Selecting a trigger requires no additional `uiselect` write, because `uiselect` already holds the trigger access value.

While `uiselect` holds the trigger access value, attempts to access `uireg6` raise an illegal-instruction exception.

[[utrig-select]]
==== Trigger Selection

While `uiselect` holds the trigger access value, `uireg5` accesses the same underlying state as `tselect`: writing `uireg5` updates the trigger index that `tselect` reads, and vice versa. When S-mode is implemented, `sireg5` and `vsireg5` also access this index, as specified in <<sstcfg-trigger-select>>. Each hart has one trigger selection index.

The trigger selection index accessed through `uireg5` is WARL and follows the same legal-value conversion as Sdtrig `tselect`. Writes of values greater than or equal to the number of supported triggers may result in a different value than what was written, or may select a trigger where `tdata1`.TYPE=0. To verify that a written index is valid, software can read back `uireg5` and check that it holds the written value, then read `uireg` and check that TYPE is non-zero.

Accesses to `uireg5` are not subject to the field modifications in <<utrig-field-mods>>, the type constraints in <<utrig-type-constraints>>, or the `DMODE` read-only-0 rule in <<utrig-dmode>>. They read and write the selection index regardless of the configuration of the selected trigger. A write to `uireg5` changes only the selection index and does not modify the `tdata*` state of any trigger.

Software must save and restore the selection index when switching trigger access between M-mode, S/HS-mode, VS-mode, and U/VU-mode. Higher-privilege software must not assume that `tselect` retains its value across delegated U-mode accesses.

==== Virtualization

When V=1, accesses from VS-mode or VU-mode to `uiselect` and `uireg*` follow <<sucsrind, Sucsrind>> virtualization rules. Field relocations that apply to VS-mode or VU-mode accesses are specified in <<utrig-field-mods>>.

[[utrig-field-mods]]

`uireg*` provides access to a subset of the fields in the native trigger registers, and in some cases fields are relocated. The field modifications that apply when trigger registers are accessed via `uireg*` are documented below.

[NOTE]
The bit positions for the M, S, U, VS, and VU fields vary based on the trigger type specified by `tdata1`.TYPE; see _The RISC-V Debug Specification_ cite:[dbgspec], Chapter 5.7.

[[utrig-type-constraints]]
==== Type Delegation Constraints

The trigger types supported through `uiselect` and `uireg*` are `mcontrol6`, `icount`, and disabled (Sdtrig type 15). When the selected trigger's `tdata1`.TYPE is any other value, including `mcontrol`, `itrigger`, `etrigger`, `tmexttrigger`, legacy, custom, and reserved types, accesses through `uireg`, `uireg2`, `uireg3`, and `uireg4` are read-only 0 and writes are ignored.

[NOTE]
`itrigger` and `etrigger` are excluded because Sdtrig fires them just before the first instruction of the trap handler, and each `tdata2` bit selects a cause number interpreted in the mode in which that handler executes. The S/HS and VS views can filter those bits with `mideleg`/`medeleg` or `hideleg`/`hedeleg`, as specified in <<sstcfg-type-constraints>>. U-mode and VU-mode do not execute trap handlers and have no equivalent delegation register, so this interface does not define a writable subset of `tdata2`.

When `tdata1`.TYPE is a supported type, `uireg4` reads `tinfo` with bits corresponding to types not supported through this interface read-only 0. Writes to `tdata1`.TYPE through `uireg` are WARL and may only select a type supported through this interface.

[NOTE]
`mcontrol` is deprecated and is not supported through this interface. Use `mcontrol6` for address/control triggers.

[[utrig-dmode]]
==== DMODE Interaction

When the hart is not in Debug Mode and the selected trigger has `tdata1`.DMODE=1, the trigger is reserved for Debug Mode use. VS-mode, U-mode, and VU-mode accesses through `uireg` through `uireg4` follow the owner rule in <<dmode-mgmt>>: they read 0 and writes are ignored. When the hart is in Debug Mode, these accesses follow the field modifications in this section together with the base Sdtrig `DMODE` rules.

M-mode and S/HS-mode accesses to `uireg` through `uireg4` while `uiselect` holds the trigger access value are management accesses in the U view, as specified in <<dmode-mgmt>>. The U view covers only the U mode-enable field, so S/HS-mode can save, park, and restore `DMODE`=1 triggers that match only in U-mode. These accesses use the U-mode field modifications and type constraints in this chapter.

When switching between U-mode application contexts, S/HS-mode software should follow the procedure in <<dmode-mgmt>> using `uiselect` and `uireg` through `uireg5`. VU-mode context is managed by HS-mode through the VS view, as specified in <<sstcfg-lower-dmode>>.

[NOTE]
When the hart is not in Debug Mode and `uireg` through `uireg4` all read as zero for the trigger index held in `uireg5`, VS-mode, U-mode, or VU-mode software cannot use the selected slot through this interface. The slot may be reserved by Debug Mode (`DMODE`=1), may have an unsupported `tdata1`.TYPE, or may have `tdata1`.TYPE=0. Software should try the next trigger index. An all-zero read of aliases 1–4 does not distinguish these cases. S/HS-mode management accesses are governed separately above. Sdtrig `chain` WARL on a visible trigger still depends on a neighboring trigger's `DMODE`; this interface does not redefine that WARL. An external debugger whose <<dbgaccpriv, debug access privilege>> is U-mode or VU-mode uses the same interface from Debug Mode, where `DMODE`=1 is visible and writable, so it can program `ACTION`=1 in accordance with Sdtrig.

=== User Trigger State Access Control

When S-mode is implemented, U-mode access requires `mstateen0`.TR=1 and `sstateen0`.TR=1. When V=1, VU-mode access additionally requires `hstateen0`.TR=1. The access control is checked in the following order:

. If the privilege mode is less privileged than M-mode and `mstateen0`.TR=0, attempts to access `uireg`, `uireg2`, `uireg3`, `uireg4`, or `uireg5` while `uiselect` holds the trigger access value raise an illegal-instruction exception.
. Otherwise, if V=1 and the privilege mode is VS or VU and `hstateen0`.TR=0, attempts to access `uireg`, `uireg2`, `uireg3`, `uireg4`, or `uireg5` while `uiselect` holds the trigger access value raise a virtual-instruction exception.
. Otherwise, if V=0 and the privilege mode is U and `sstateen0`.TR=0, attempts to access `uireg`, `uireg2`, `uireg3`, `uireg4`, or `uireg5` while `uiselect` holds the trigger access value raise an illegal-instruction exception.
. Otherwise, if V=1 and the privilege mode is VU and virtual `sstateen0`.TR=0, attempts to access `uireg`, `uireg2`, `uireg3`, `uireg4`, or `uireg5` while `uiselect` holds the trigger access value raise a virtual-instruction exception.

When S-mode is implemented, VS-mode accesses through this interface use the VU-mode field view and are controlled by `hstateen0`.TR; U-mode accesses are controlled by `sstateen0`.TR; and VU-mode accesses are controlled by both `hstateen0`.TR and virtual `sstateen0`.TR. S/HS-mode management accesses use `mstateen0`.UCSRIND and `mstateen0`.TR and are not restricted by these lower-level state-enable bits.

When S-mode is not implemented, `sstateen0` does not exist. In this case, `mstateen0`.TR alone controls U-mode access to `uireg` through `uireg5` while `uiselect` holds the trigger access value. An illegal-instruction exception is raised for those accesses when `mstateen0`.TR=0.

M-mode accesses to `uireg` through `uireg5` while `uiselect` holds the trigger access value are not restricted by TR and are permitted. When S-mode is implemented and `mstateen0`.TR=1, S/HS-mode accesses to those CSRs are likewise permitted. Those accesses use the U-mode field modifications and type constraints in this chapter, including the management access to `DMODE` in <<utrig-dmode>>.

S/HS-mode management accesses are architectural accesses and do not require an SBI. When Smstateen is implemented, they remain subject to `mstateen0`.UCSRIND and `mstateen0`.TR. `sstateen0`.TR and `hstateen0`.TR control VS-mode, U-mode, and VU-mode software access; they do not restrict S/HS-mode management accesses.

When `mstateen0`.TR=0, `sstateen0`.TR is read-only 0. When V=1 and `hstateen0`.TR=0, virtual `sstateen0`.TR is read-only 0.

The TR bit is bit 3 in `sstateen0`.

[NOTE]
See the Sscsrind and Sucsrind specifications cite:[indirectcsr] for how bit 60 (CSRIND) in `mstateen0` and `hstateen0` restricts access to `siselect` and `sireg*` from privilege modes less privileged than M-mode, including VS-mode when V=1. Access to `uiselect` and `uireg*` is gated by the UCSRIND bit (bit 4) of `mstateen0`, `hstateen0`, and `sstateen0`, as specified in <<sucsrind, Sucsrind>>. The CSRIND and UCSRIND bits provide blanket control over the Sscsrind and Sucsrind indirect CSR infrastructure, while TR provides trigger-specific delegation control.

=== Access to `tcontrol`

The `tcontrol` CSR is not accessible through the delegated indirect interface. `tcontrol` remains M-mode only.

When a delegated trigger with ACTION=0 fires in U-mode or VU-mode, a breakpoint exception is taken through the normal privilege trap mechanism. ACTION=1 follows Sdtrig and enters Debug Mode, except that it does not match or fire while external debug is disallowed for the hart's current privilege mode, as specified in <<Sdsecextdbg>>. Other ACTION values retain the behavior defined by Sdtrig.

[NOTE]
`tcontrol`.MTE and `tcontrol`.MPTE affect only triggers with ACTION=0 while the hart is in M-mode, as specified by Sdtrig. They do not disable triggers that match or fire in a less-privileged mode, and they do not affect ACTION=1. Delegated ACTION=0 triggers follow Sdtrig's native-trigger match and reentrancy rules. Because `tcontrol` is not accessible from S-mode, it does not provide a less-privileged analogue of the M-mode handler-reentrancy control.

=== Debugger Access from U-mode and VU-mode

When Smuedbgsec is implemented, `mdbgen`=0, `SEDBGEN`=0, and `UEDBGEN`=1, an external debugger whose <<dbgaccpriv, debug access privilege>> is U-mode can access triggers through the `uiselect`/`uireg*` interface, provided that the applicable TR bits permit access (`mstateen0`.TR=1 and, when S-mode is implemented, `sstateen0`.TR=1).

When Smuedbgsec is implemented, `mdbgen`=0, `SEDBGEN`=0, `VSEDBGEN`=0, and `VUEDBGEN`=1, an external debugger whose debug access privilege is VU-mode uses the same interface, provided that `mstateen0`.TR=1, `hstateen0`.TR=1, and virtual `sstateen0`.TR=1.

[NOTE]
This access path is one of the primary motivations for Sutcfg: without it, an external debugger restricted to U-mode or VU-mode privilege has no path to trigger state.

=== Trigger Allocation

When the applicable TR bits permit access, U-mode and VU-mode can access delegated trigger state through `uiselect`/`uireg*` (subject to DMODE restrictions and type-specific constraints). When S-mode is implemented and `mstateen0`.TR=1, S/HS-mode can use the same access path to manage U-mode trigger context.

`DMODE` takes priority over delegated VS-mode, U-mode, and VU-mode access, as specified in <<dmode-mgmt>>. Higher-privilege software can reconfigure triggers with `DMODE`=0 through its own interface, overriding lower-privilege configuration. S/HS-mode can manage `DMODE`=1 triggers within the U view as specified in <<utrig-dmode>>, and HS-mode manages VS-mode and VU-mode trigger context as specified in <<sstcfg-lower-dmode>>. Debug Mode can reclaim a trigger through the corresponding delegated interface.

Software must manage trigger allocation cooperatively. TR enables delegated trigger access but does not identify per-trigger ownership. There is no per-trigger hardware allocation. Before setting the applicable TR bit, higher-privilege software should clear its own mode-enable bits on any trigger it is exposing.

* M-mode allocates triggers between its own use and lower-privilege delegation.
* When S-mode is implemented, S/HS-mode software allocates triggers between its own use and U-mode delegation, and sets `sstateen0`.TR=1 once it is prepared to delegate trigger access to U-mode.
* When S-mode is not implemented, M-mode firmware sets `mstateen0`.TR=1 once it is prepared to delegate trigger access to U-mode.

=== Dependencies

Sutcfg depends on the following extensions:

* Sdtrig -- Base trigger extension defining trigger CSRs and types.
* <<sucsrind, Sucsrind>> -- User-mode indirect CSR interface (`uiselect`/`uireg*`).
* <<smtdeleg, Smtdeleg and Sstcfg>> (required when S-mode is implemented) -- Define S-mode trigger access through `siselect`/`sireg*`.
* Smstateen / Ssstateen -- State enable framework for access control cite:[smstateen].
* H extension (optional) -- Required for trigger delegation controls in VS/VU-mode.

=== Summary of New State

Sutcfg introduces no new CSRs. It uses the trigger access value in the `uiselect` select space and `uireg` through `uireg5` as specified in <<utrig-access>>.
